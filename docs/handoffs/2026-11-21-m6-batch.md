## Retry policy chosen for on-demand discussion drafts

There are at most 2 attempts, and the retry happens only on `provider_unavailable` (HTTP 500/502/503). The delay is 1.5 s × jitter (0.75–1.5 s). The configured timeout (30 s) is the total budget: the second attempt's SDK timeout is reduced to whatever time remains, and the retry is skipped if less than 10 s remain.

Why: your observed 503s returned in 3.5–7 s, so one retry fits inside the budget.

* A 429 is not retried, because a retry seconds later would hit the same per-minute limit.
* A timeout is not retried, because it has already used the budget.
* A validation failure is never retried, because retrying until something passes would hide whether Gemini or the validator is wrong.

## Open questions

* **Daily quota detection:** it relies on Google's documented `QuotaFailure.quotaId` containing `PerDay`. This was not verified against a live 429. A daily 429 without it would be retried as per-minute and then still stop the run (at most 4 calls).
* **`--min-interval`** **default (6 s):** this assumes Flash-Lite allows about 10–15 requests per minute on your account. Adjust it if your limits differ.
* **`RetryInfo.retryDelay`** in 429 responses is not used. Plain exponential backoff is used instead.
* **Choice of batch:** I used April for the dry run as the latest published batch. Tell me if you want a different one.

## Known limitations

* **Summaries regenerate only when you run the batch.** After a new month is published, you must run the batch for it; nothing triggers it automatically, by design, because it makes live calls.
* **Rejected outputs leave no stored draft.** Those customers show deterministic text and are attempted again on the next run, which uses quota.
* **Retries only apply to RM discussion drafts.** In the smoke script, `gemini_smoke.py` deliberately keeps a single attempt.
* **A crash can leave a reservation behind.** If the process crashes mid-request, that customer is blocked for up to the worst-case reservation time (≈2.5 min at a 30 s timeout) before the existing expiry recovery clears it.
* **No live call was made in this work.** Live acceptance of generated summaries remains pending your run.

### Risks and open questions
- **More validation rejections are possible.** Without the enum, Gemini may cite unknown IDs or the wrong number of IDs more often. The validator rejects them, deterministic text is shown, and `--keep-rejected` records them for your review.
- **The 400 may not be fully fixed.** If "too many states" persists, the next smallest step would be removing the top-level `maxItems` too, since the validator already enforces counts. Only a live run can confirm either way.

- **Timeouts do not count toward the outage rule,** as you specified; only `provider_unavailable` does.
